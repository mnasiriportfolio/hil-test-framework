Chapter 3

Layer 3 — the Hardware Abstraction Layer

The HAL is the only layer that touches real instruments. It has two halves: the interfaces (the promises) and the drivers (the objects that keep them).

The four interfaces

From interfaces.py, the vocabulary Layer 2 is allowed to use:

class SignalGenerator(Instrument, Protocol):   # drives stimulus
    def configure_sine(self, channel, amplitude_vpp, frequency_hz, offset_v=0.0): ...
    def add_harmonic(self, channel, order, amplitude_vpp): ...
    ...

class Multimeter(Instrument, Protocol):        # reads scalars
    def measure_dc_voltage(self) -> float: ...
    def measure_ac_current_rms(self) -> float: ...

class Oscilloscope(Instrument, Protocol):      # captures time-domain traces
    def capture_relay(self, relay: str, gate_ms: float) -> Waveform: ...

class DeviceUnderTest(Instrument, Protocol):   # the DUT's own telemetry
    def get_relay_states(self) -> dict[str, bool]: ...
    def read_analog_output(self, channel: int) -> float: ...
Why four, not one? Each role is a different job. Splitting them means a test that only needs a multimeter doesn't depend on oscilloscope methods — smaller contracts, fewer surprises.

A driver keeps a promise

From sim_drivers.py. Notice it extends BaseDriver (for the lifecycle) and happens to match the SignalGenerator protocol (for Layer 2). The two are independent:

class SimSignalGenerator(BaseDriver):
    def __init__(self, bench: SimulatedBench, name: str = "SIM-AFG") -> None:
        super().__init__(name)
        self.bench = bench

    def configure_sine(self, channel, amplitude_vpp, frequency_hz, offset_v=0.0):
        self._require_connection()
        ch = self.bench.channels[channel]
        ch.waveform = "SIN"
        ch.amplitude_vpp = amplitude_vpp
        ch.frequency_hz = frequency_hz
        ch.offset_v = offset_v
Analogy BaseDriver is the staff handbook every employee follows (clock in / clock out). The SignalGenerator protocol is the job description for the "signal" role. A real employee (SimSignalGenerator) does both.
What breaks if a driver forgets a method Because the protocol is @runtime_checkable, a missing method means the object no longer counts as a SignalGenerator — you find out immediately, not after wiring it into a test.

The swap that proves the point

Every simulated driver shares one SimulatedBench (next chapter). To move to real hardware you'd write, say, a ScpiSignalGenerator(BaseDriver) that sends SCPI over a socket. Layer 2 would not change one line — it still just asks for a "signal generator". That is the payoff of the interfaces.

Key concepts introduced

inheritance (extends)super().__init__composition (has-a bench)role interfaces

Quiz 1 — SimSignalGenerator inherits BaseDriver but not SignalGenerator. How can Layer 2 accept it?

Structural typing: it has the methods the SignalGenerator protocol lists, so it satisfies the protocol without inheriting it.

Quiz 2 — What does super().__init__(name) do here?

Runs BaseDriver.__init__ so the connection flag and name get set up before the subclass adds its own self.bench.

Exercise 3. Sketch (just the method names) a ScpiMultimeter(BaseDriver) that would satisfy the Multimeter protocol. You don't need real SCPI — the point is to see that Layer 2 wouldn't notice the difference.
