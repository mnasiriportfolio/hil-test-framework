Chapter 5

Config & plans — data instead of code

Two kinds of external data steer the framework: one bench config (which bench) and many plans (which scenarios). Editing them re-targets the framework without touching Python.

The bench config, validated on load

From config_loader.py. It reads YAML and fails loudly if the shape is wrong — a typo should stop you at load time, not mid-test:

def load_config(path: str | Path) -> BenchConfig:
    data = yaml.safe_load(Path(path).read_text(encoding="utf-8")) or {}
    for key in ("bench", "instruments", "simulation"):
        _require(data, key, "top level")
    sim_raw = data["simulation"]
    sim = SimConfig(
        volts_to_amps=float(sim_raw.get("volts_to_amps", 10.0)),
        overcurrent_trigger_a=float(sim_raw.get("overcurrent_trigger_a", 200.0)),
        ...
    )
    return BenchConfig(name=..., simulate=..., instruments=..., sim=sim, raw=data)
Why turn YAML into a BenchConfig dataclass? Raw dictionaries invite typos (cfg["trigger"] vs cfg["triger"]). A dataclass gives named, typed fields the editor can check — the config becomes a real object, not a bag of strings.

A plan is a table of scenarios

config/overcurrent_plan.csv:

name,enabled,trigger,tolerance_pct,detect_max_ms,hold_min_s
slow_ac,true,200,3,2000,3
fast_dc,false,500,3,10,3
validation_ac,false,350,3,1500,3

Loaded into Scenario objects by plan.py, which also rejects duplicate names and keeps any extra columns:

if name in seen:
    raise ValueError(f"plan {path.name}: duplicate scenario '{name}'")
seen.add(name)
Analogy The plan is a recipe card; enabled is a sticky note saying "make this one tonight". To cook a different dish you swap cards, not the kitchen.

What breaks with duplicate names Two rows called slow_ac would silently overwrite each other's results in the report. The loader refuses them up front, so the mistake can't reach a run.

Pure math, separately testable

The spec comparisons are pure functions — no hardware, no state — so they can be unit-tested directly:

def tolerance_window(trigger: float, tolerance_pct: float) -> tuple[float, float]:
    delta = trigger * tolerance_pct / 100.0
    return trigger - delta, trigger + delta

def timing_ok(measured_ms: float, limit_ms: float) -> bool:
    return 0.0 < measured_ms <= limit_ms
Why keep these pure? Pure functions are the easiest code to trust: give inputs, check outputs, done. See tests/unit/test_plan.py — the whole spec logic is verified without a bench.

data-driven designfail-fast validationpure functionsdataclass over dict

Quiz 1 — To run the framework against a new device, what do you change?

The YAML config (bench + simulated behaviour) and the CSV plans (scenarios). No Python.

Quiz 2 — Why are tolerance_window and timing_ok free functions, not methods on a bench?

They're pure spec maths with no hardware dependency, so they belong where they can be tested in isolation and reused by any test type.

Exercise 5. Flip fast_dc to enabled=true in the overcurrent plan and run the example. Watch a second scenario appear in the report. Then set an impossible detect_max_ms (say 10) and see it fail — the plan drove the outcome, not the code.
