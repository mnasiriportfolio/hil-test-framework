Chapter 7

The keyword algorithms — the brain

This is where a test happens: drive stimulus, read instruments, decide, publish. The keywords in keywords.py speak only interface methods and the event bus — never a volt or an IP.

Finding an edge on the scope

The threshold is derived from the trace, half-way between its low and high level — not hardcoded. A 3.3 V logic relay, a 5 V one and a 24 V industrial one all work with no reconfiguration:

def auto_threshold_v(wf: Waveform) -> float | None:
    if not wf.samples:
        return None
    lo, hi = min(wf.samples), max(wf.samples)
    if hi - lo < _MIN_EDGE_SWING_V:
        return None
    return (lo + hi) / 2.0

A flat trace legitimately has no threshold — that is a relay that never moved, and returning None says so instead of inventing an edge. From there, edges_ms finds the rising edge and then, starting from it, the falling one; pulse_width_ms is the difference.

Why the fall is searched only after the rise A trace that starts high — a relay still latched from the previous scenario — would otherwise read as a pulse that ended at t=0, reporting a hold of zero for a relay that was never released.
Analogy It's a stopwatch that starts at capture, splits when the relay "lights up", and stops when it goes dark. Return inf and the timing check reads "the light never came on".

The overcurrent test, end to end

ratio = calibrate_volts_to_amps(controller)      # measured, never read from config
_publish_calibration(bus, suite, case, ratio)

sg.output_off(ch)                                 # not-driven baseline first
baseline = dmm.measure_ac_current_rms()
idle = not dut.get_relay_states()["overcurrent"]
_publish(bus, suite, case, "Relay idle before stimulus", ..., _outcome(idle))

sg.configure_sine(ch, vpp_for_current(sc.trigger * TRIGGER_OVERDRIVE, ratio), 50.0)
sg.output_on(ch)
measured = dmm.measure_ac_current_rms()
_publish(bus, suite, case, "Trigger level", ...,
         _outcome(within_tolerance(measured, sc.trigger, sc.tolerance_pct)))

wf = osc.capture_relay("overcurrent", gate_ms=capture_gate_ms(sc))   # ONE capture
t_ms = rising_edge_ms(wf)
_publish(bus, suite, case, "Detection time (scope)", ...,
         _outcome(timing_ok(t_ms, sc.detect_max_ms)))

hold_s = pulse_width_ms(wf) / 1000.0                                 # TWO measurements
_publish(bus, suite, case, "Relay hold (scope)", ...,
         _outcome(hold_ok(hold_s, sc.hold_min_s)))
Two things worth stopping on. First, the ratio is measured at the top of every case. It would be easy to read it from config — it is right there — but on a real bench it is a property of the probe and the cabling on the day, and a stale one is invisible: every level is off by the same factor, so the numbers still look plausible.

Second, TRIGGER_OVERDRIVE. Commanding exactly the threshold is undefined — generators have finite command resolution, detectors have hysteresis — so a test that means "cross it" states its margin instead of hoping.
Notice what's absent. No volts-to-amps constant, no socket, no VISA call. The keyword asks a SignalGenerator, a Multimeter and an Oscilloscope to do their jobs, and never learns which of the four transports it is holding.

Self-calibration — the clever bit

The analog-output test measures error, and if it's too big it fixes the device and re-checks — reporting both steps honestly:

err_pct = abs(out - requested) / requested * 100.0
ok = err_pct <= sc.tolerance_pct
_publish(bus, ..., "output error (pre-cal)", ..., _outcome(ok, borderline=True))  # PASS or CHECK

if not ok:
    correction = requested / out
    dut.apply_analog_correction(correction)
    out2 = dut.read_analog_output(channel)
    err2 = abs(out2 - requested) / requested * 100.0
    _publish(bus, ..., "auto-calibration", ..., _outcome(err2 <= sc.tolerance_pct))
The test verifies the device — not the other way round. It measures reality, compares to the plan's spec, and flags mismatches as CHECK rather than bending a number to make it pass. That honesty is the difference between a test that protects you and one that lies to you.
What breaks if you fudge a measurement to match spec A real defect sails through. The whole value of an automated bench is that it tells you the uncomfortable truth every time — so the code is written to preserve that truth.

Quiz 1 — Why does rising_edge_ms return inf instead of, say, 0?

0 would look like "detected instantly". inf is unmistakably "never crossed", which timing_ok then correctly reports as a failure.

Quiz 2 — Why is the pre-cal step a CHECK, not a FAIL, when out of tolerance?

Because it's expected and about to be corrected. FAIL is reserved for a result the framework can't fix; the post-cal step is the real PASS/FAIL.
