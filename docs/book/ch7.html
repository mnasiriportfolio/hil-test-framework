Chapter 7

The keyword algorithms — the brain

This is where a test happens: drive stimulus, read instruments, decide, publish. The keywords in keywords.py speak only interface methods and the event bus — never a volt or an IP.

Finding an edge on the scope

Detection timing comes from the first sample that crosses half of the 0→3.3 V relay swing:

def rising_edge_ms(wf: Waveform, threshold_v: float = 1.65) -> float:
    for i, v in enumerate(wf.samples):
        if v >= threshold_v:
            return i * wf.dt_s * 1000.0
    return float("inf")   # no crossing -> no edge
Analogy It's a stopwatch that starts at capture and stops the instant the relay "lights up". Return inf and the timing check reads "the light never came on".

The overcurrent test, end to end

def run_overcurrent_case(controller, sc, bus) -> None:
    sg, dmm, osc = controller.signal_generator, controller.multimeter, controller.oscilloscope
    ch = controller.config.sim.current_channel

    sg.configure_sine(ch, _vpp_for_current(controller, sc.trigger), 50.0)
    sg.output_on(ch)
    measured = dmm.measure_ac_current_rms()
    trig_ok = within_tolerance(measured, sc.trigger, sc.tolerance_pct)
    _publish(bus, suite, case, "Trigger level", ..., _outcome(trig_ok))

    wf = osc.capture_relay("overcurrent", gate_ms=sc.detect_max_ms + 500.0)
    t_ms = rising_edge_ms(wf)
    _publish(bus, suite, case, "Detection time (scope)", ...,
             _outcome(timing_ok(t_ms, sc.detect_max_ms)))
Notice what's absent. No volts-to-amps, no socket, no NI call. _vpp_for_current converts a target current to generator volts using the bench calibration, but the keyword itself just asks a SignalGenerator and an Oscilloscope to do their jobs.

Self-calibration — the clever bit

The analog-output test measures error, and if it's too big it fixes the device and re-checks — reporting both steps honestly:

err_pct = abs(out - requested) / requested * 100.0
ok = err_pct <= sc.tolerance_pct
_publish(bus, ..., "output error (pre-cal)", ..., _outcome(ok, borderline=True))  # PASS or CHECK

if not ok:
    correction = requested / out
    dut.apply_analog_correction(correction)
    out2 = dut.read_analog_output(channel)
    err2 = abs(out2 - requested) / requested * 100.0
    _publish(bus, ..., "auto-calibration", ..., _outcome(err2 <= sc.tolerance_pct))
The test verifies the device — not the other way round. It measures reality, compares to the plan's spec, and flags mismatches as CHECK rather than bending a number to make it pass. That honesty is the difference between a test that protects you and one that lies to you.

What breaks if you fudge a measurement to match spec A real defect sails through. The whole value of an automated bench is that it tells you the uncomfortable truth every time — so the code is written to preserve that truth.

Quiz 1 — Why does rising_edge_ms return inf instead of, say, 0?

0 would look like "detected instantly". inf is unmistakably "never crossed", which timing_ok then correctly reports as a failure.

Quiz 2 — Why is the pre-cal step a CHECK, not a FAIL, when out of tolerance?

Because it's expected and about to be corrected. FAIL is reserved for a result the framework can't fix; the post-cal step is the real PASS/FAIL.
